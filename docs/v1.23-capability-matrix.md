# BlackList next-generation capability matrix

## Product direction

BlackList should maximize protection through supported Android APIs first, then expose optional privileged adapters only when a device explicitly grants them. The product must never promise that a privileged path can override Telecom, OEM dialers, carrier behavior, or Android privacy boundaries on every device.

| Capability | Official Android path | Root/Shizuku path | Play distribution posture | Priority |
|---|---|---|---|---|
| Exact, prefix, suffix, contains, range and country rules | Local rule engine + CallScreeningService | Not needed | Safe core feature | P0 |
| Reject incoming call | `CallResponse.setRejectCall(true)` | Not needed | Safe core feature | P0 |
| Disallow/block incoming call | `CallResponse.setDisallowCall(true)` | Not needed | Safe core feature | P0 |
| Silence ringtone | `CallResponse.setSilenceCall(true)` | Not needed | Safe, but must document that system UI/logs may remain visible | P0 |
| Suppress BlackList notifications | Local notification policy and channels | Not needed | Safe | P0 |
| Skip call-log or missed-call artifacts | `setSkipCallLog` / system-dependent response behavior | Device-specific only | Must be tested per Android version | P1 |
| Unknown/private caller policies | Call presentation metadata plus local settings | Not needed | Safe | P0 |
| International/country policies | Local libphonenumber classification | Not needed | Safe if no cloud lookup | P1 |
| Repeated-call / first-contact policies | Local call history generated by the app and bounded signals | Not needed | Safe when no background Call Log access is required | P1 |
| Contact-group rules | Contacts provider after explicit consent, or user-imported groups | Not needed | Requires careful permission declaration | P1 |
| SMS spam classification | Default SMS role or explicit, policy-compliant user picker | Privileged access varies by device | Play policy risk; keep opt-in and separate build strategy available | P1 |
| SMS deletion/quarantine | Default SMS app capabilities | Root may alter app/database state but is unsafe and OEM-specific | Do not implement destructive hidden deletion | P2 |
| Caller-ID/reputation lookup | User-imported offline lists | Not needed | No network by default; no silent cloud lookup | P1 |
| DND/notification policy integration | User grants Notification Policy Access | Shizuku/root cannot be assumed to replace user consent | Safe with explicit settings flow | P1 |
| Device-wide call interception outside Telecom | Not generally available to normal apps | Root/Shizuku may expose device-specific mechanisms, not a stable universal API | Keep experimental and disabled by default | P2 |
| OEM dialer/system phone database modification | Not available through supported public APIs | Root-only and highly device-specific | Never claim universal support; avoid destructive mutation | P2 |

## Planned release slices

### v1.23.x: protection intelligence and observability

The next implementation slice should add a richer local policy model for caller presentation, international calls, repeated calls, and first-contact handling; a clear decision trace; per-source privacy controls; an offline import/export format for reputation lists; and compatibility diagnostics. Every decision must remain deterministic and testable without network access.

### v1.24.x: user-controlled system integrations

The following slice should integrate Notification Policy Access and more complete role/capability remediation, add rule-level notification and call-log behavior where Android exposes it, and improve OEM compatibility diagnostics. It should not use AccessibilityService or hidden APIs as a shortcut for call interception.

### v1.25.x: optional Shizuku capability adapter

Only after the supported path is complete should the project add an optional Shizuku adapter. The adapter must use the official Shizuku API, check service availability and permission, expose a visible capability status, request confirmation for every privileged action, and return `UNSUPPORTED` rather than attempting undocumented transaction codes. No Root/Shizuku operation should run in the call-screening hot path.

### Separate privileged build, if needed

If a future feature genuinely requires root-only behavior, it should be a separate opt-in build with an explicit warning, device/API compatibility matrix, reversible operations, a dry-run mode, audit logs, and no destructive modification of Telecom, SMS, or OEM databases. The Play build must remain fully functional without it.

## Non-negotiable safety and privacy boundaries

BlackList will not use AccessibilityService to impersonate a dialer, hidden APIs, undocumented Telecom transactions, ADB commands embedded in the app, silent SMS deletion, or cloud uploads of contacts, call history, messages, or phone numbers. Any privileged operation must be user initiated, reversible where possible, narrowly scoped, and visible in the app's diagnostics.
